# Step 21 — Backward Integrity Audit and Release Acceptance

## Purpose
Make release contents auditable in reverse: verify each packaged file against the manifest, detect untracked/missing files, exclude Python bytecode, and validate the ZIP container before distributing it. This is artifact integrity, not proof of semantic correctness or hardware durability.

## Release acceptance checks
1. Manifest file list exactly matches tracked package files (excluding the manifest itself and generated bytecode).
2. No `__pycache__`, `.pyc`, or `.pyo` artifacts are included.
3. ZIP CRC/member integrity check passes.
4. Backup/restore positive and negative tests pass, including target-preservation cases.
5. Full unit suite is run with warnings enabled; failures and warnings are reported separately.
6. Prior release ZIPs are checked for container integrity; hashes are recorded in the release audit report.
7. Runtime remains `simulated_only`; no external side effects or production guarantees are inferred.

## Limits
ZIP integrity does not detect a logically incorrect implementation. A manifest listing does not cryptographically authenticate a release unless a trusted manifest/signature is distributed independently. The historical ZIP checks establish readable ZIP members, not that every prior release is behaviorally equivalent.
